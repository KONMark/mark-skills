# 《详细需求文档》模板与写作要求

本模板对齐项目现有《详细需求文档》的颗粒度：每个模块先讲业务、再列资料表、再逐个功能写“用途 / 操作 / 规则”、最后汇总本模块规则；全文末尾统一列通用规则、本期不做、需要确认的事项。

## 0. 格式约定

- 顶部固定四行元信息表：文档名称、项目名称、版本、日期。
- 一级标题：`# 1.`、`# 2.`……；二级 `## 2.1`；三级 `### 2.1.1`。
- 功能标题固定格式：`### 功能 <序号>：<功能名>（M1-F01）`。
- 字段表固定三列：`字段 | 填写方式 | 说明`。
- 填写方式只允许：`必填`、`选填`、`自动`、`按方式`。
- 每个功能必须有三个小标题：`**用途**：`、`**操作**：`、`**规则**：`；没有操作的功能（如提醒类）可只写用途和规则。
- 面向工厂人员写作：短句、具体名词、主动语态；不用表名、接口、SQL、框架等实现词。
- 待确认事项集中到最后一节；正文用括号指过去，例如“（更正方式见第 13 节。）”。
- 篇幅不设上限，以写清为准；中型项目通常 1,000～3,000 行。

# 1. 文档说明

本文把第一版系统要做的功能逐个列清楚，既用于业务方确认“系统有哪些模块、每个模块能做什么”，也作为后续开发、测试和验收的依据。

阅读约定：

- **本期**：第一版要做的内容。
- **资料表**：系统里保存的一类数据。
- **字段**：资料表里的每一栏。

- 第 2 节：系统总览、使用顺序、模块清单、角色、功能总索引。

## 2. 各节写作要求

### 1 文档说明

- 说明两份文档的分工：总需求管“做什么”，本文管“怎么做”。
- 解释本文会出现的高频词，尤其是“本期”“资料表”“字段”“自动”“待确认”。
- 给出一段结构导览，让读者知道从哪里找什么。
- 明确“只写本期，不做集中列在最后”。

### 2 系统总览

- 2.1 用业务语言描述，不出现模块名堆砌。
- 2.2 按真实使用顺序，先建账号和基础资料，再走业务，最后做周期性工作。
- 2.3 流程图控制在 10 个节点以内；用 `flowchart LR`，节点名带业务动作。
- 2.4 模块总览必须包含“总需求章节”列，与总需求 §4 对齐。
- 2.5 角色表只列角色和模块级可见性；具体接口限制在通用规则里写。
- 2.6 功能总索引是全文骨架：先写它，再写各模块；每写完一个模块回填。

### 模块章节（第 3 节起）

固定四段，顺序不变：

**X.1 这个模块解决什么问题**

- 3～5 行，先讲业务场景，再讲系统动作。
- 写明“在流程中的位置”和“谁可以使用”。
- 末尾注明“对应总需求 §4.x”。

**X.2 系统保存哪些资料**

- 一张资料表一个小节，标题用业务名称，不用数据库表名。
- 有表头和明细的单据，分开写“表头”“明细”。
- 字段表三列：字段、填写方式、说明。
- 说明列写“是什么、从哪来、怎么变化”，不写技术类型。
- 通用四字段（编号、创建时间、更新时间、删除标记）可合并成一行。
- 有状态的资料表，在字段表后补状态说明：状态名、含义、进入/离开条件。

**X.3 功能清单**

- 功能顺序按员工实际使用顺序排，不按技术层次排。
- 每个功能标题带总需求编号，例如 `（M5-F05）`。
- 用途一句话；操作写步骤；规则写约束和算例。
- 操作步骤用“点击、选择、填写、核对、确认”等动作词，不写“调用接口”。
- 规则要能被测试：能写出通过和不通过的例子。
- 关键计算给一个具体算例，例如“本次 400 件、每件 2 个，需要 800 个；库存 650 个，缺 150 个”。
- 与其它模块的联动写在规则里，例如“送货不扣材料库存”。

**X.4 本模块必须记住的规则**

- 5 条以内，是该模块最容易做错的地方。
- 与 X.3 的规则不重复整段，只做提炼。

### 通用规则

- 只定义一次，各模块引用，不重复展开。
- 权限、精度、编号、追溯是最容易漂移的四类，必须集中在这里。
- 与总需求 §5.1 的分工：总需求只给一句话指向本节，本节写完整规则。

### 本期不做

- 只列用户明确确认不做的事。
- 按主题分组：生产与成品、特殊业务、价格与结算、单据异常、系统功能、不纳入管理的单据等。
- 不要写“本期暂不做”的模糊项；没想清楚的放待确认。

### 需要确认的事项

- 按主题分组，与模块顺序对应。
- 每条写清“问题 + 本期暂定处理方式”。
- 已确认的补充结论可以紧跟其后，标注“已确认补充：……”。
- 本节是全文唯一的待确认清单，正文其他位置只引用。

### 文档使用说明

- 说明与总需求的关系、范围以哪节为准、待确认如何处理、冲突时以谁为准。

## 3. 功能块的写法示例

```markdown
### 功能 5：领料前检查欠板（M5-F05）

**用途**：生产前先看材料够不够，不够的提前知道缺什么、缺多少。

**操作**：

1. 选择订单和产品。
2. 填写本次用于计算需求的产品数量。
3. 系统按当前 BOM 版本计算所需材料。
4. 没有 BOM 时，由员工人工确认本次材料及需求数量。
5. 系统将各项需求与当前可用库存比较。
6. 列出不足的材料及短缺数量。

**规则**：

- 短缺数量 = 材料需求数量 − 可用库存数量。
- 需求不超过库存时，不列为短缺。
- 检查过程不扣库存，不改变任何库存数据。
- 检查结果只是提醒，不是出库单。
- 例如：本次 400 件、每件用芯片 2 个，需要 800 个；库存 650 个，提示芯片缺 150 个。
- 检查后库存仍可能被其他订单领走；是否需要预留待确认（见第 13 节）。
```

## 4. 常见错误

| 错误 | 改法 |
| --- | --- |
| 功能块只有规则，没有操作步骤 | 按员工实际点击顺序补操作 |
| 规则写成“合理处理”“适当提示” | 改成可判定的条件与结果 |
| 字段说明写成数据库类型 | 写业务含义、来源、变化方式 |
| 同一精度规则在多个模块各写一遍 | 在通用规则定义一次，模块内引用 |
| 新功能只出现在详细需求 | 先回写总需求并确认，再补详细需求 |
| 把未确认事项写进“本期不做” | 移到待确认，写清暂定处理方式 |
| 模块开头直接列字段 | 先用 3～5 行讲清业务和位置 |
