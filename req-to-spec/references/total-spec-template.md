# 《总需求文档》模板与写作要求

本模板对齐项目现有《总需求文档》的版式：顶部元信息表、编号一级标题、粗体引导词加列表、括号内标注待确认、结尾说明文档关系。生成时保持这些习惯，不要另创风格。

## 0. 格式约定

- 顶部固定四行元信息表，字段为：文档名称、项目名称、版本、日期。
- 一级标题：`# 1.`、`# 2.`……；二级标题：`## 1.1`、`## 1.2`……。
- 段落在前，列表在后；先给结论，再补细节。
- 引导词用粗体加冒号，例如 `**产品一句话**：`、`**职责**：`。
- 流程用有序列表；并列项用 `-`；清单项可加粗名称。
- 未确定内容写在括号里：`（……待确认。）`。不另开“待确认”大节，详细汇总放在《详细需求文档》最后一节。
- 不写字段表，不写点击步骤，不写技术实现；这些属于详细需求。
- 篇幅参考：中型项目 150～300 行；超过 400 行通常说明把详细需求的内容写进来了。

## 2. 各节写作要求

### 表头

- 文档名称固定为“总需求文档”。
- 项目名称采用“项目代号｜系统全称”，与详细需求保持一致。
- 版本从用户材料或目录名取值，默认 `v1.0`。
- 日期使用生成当天，格式 `YYYY-MM-DD`。

### 1 产品介绍

- 产品一句话只写一句，必须包含“给谁用、解决什么、得到什么”。
- 产品定位写第一版边界，不写愿景口号。
- 业务背景写现状和问题，不写解决方案细节。
- 问题列表每条一句话，能被后文范围或流程对应上。

### 2 范围

- 本期要做只列模块和一句话职责，详细职责放到第 4 节，避免重复。
- 明确不做必须是用户明确确认过的内容；只是没想清楚的，放待确认，不放这里。
- 按“使用端 / 特殊业务 / 其他端”分组，和现有模板一致。
- 范围以本节为准这句话要保留，便于后续仲裁。

### 3 核心流程

- 主流程按业务发生顺序编号，步骤名用动词短语。
- 每一步写清“做什么、涉及哪个模块”，必要时写出输入输出。
- 流程末尾补一段边界说明，指出容易混淆的地方（例如“完工”与“交货”不是一回事）。
- 其他重要流程写查询、追溯、异常前置处理等非主链路流程，按“粗体流程名 + 有序列表”组织。

### 4 模块明细

这一节吸收原《具体需求》的模块骨架，是总需求的主体。

- 4.1 模块总表：一行一个模块，职责控制在 20 字以内；使用角色写“所有成员”或“仅管理员”等；流程位置写“前置流程”“主流程第 2～4 步”“系统管理”。
- 每个模块按固定顺序写：职责 → 使用角色 → 流程位置 → 关键主体 → 关键状态 → 功能清单 → 关键规则。
- 关键主体只列实体名和 3～6 个关键字段名，不展开字段类型和必填规则。
- 关键状态写状态名、含义、进入/离开条件；没有明确状态机的模块写“不设状态”并说明原因。
- 功能清单一行一个功能，动词开头，带 `Mx-Fyy` 编号。编号规则：`M` + 模块序号 + `-F` + 两位功能序号。编号生成后不重排。
- 关键规则只写跨功能的约束（例如库存不足不允许出库、同一送货明细不能重复计费），不写操作步骤。
- 模块顺序与详细需求一致：前置流程 → 主流程 → 系统管理。

### 5 项目描述与通用要求

- 项目描述保留现有模板的写法：一段说明系统形态和部署，一段说明使用人数、数据量、性能与并发，一段说明安全和备份。
- 所有未定项用括号标注，例如“（服务器配置、操作系统和备份要求待确认。）”。
- 全局口径不在本文重复展开，只给一句话指向详细需求的通用规则章节。

### 6 文档关系

- 固定说明两份文档的分工和优先级。
- 明确功能编号以总需求为准。
- 明确待确认内容不作为承诺。

## 3. 常见错误

| 错误 | 改法 |
| --- | --- |
| 在模块明细里列完整字段表 | 只留实体名和关键字段名，字段表放详细需求 |
| 把功能写成操作步骤 | 功能清单只写动词短语，步骤放详细需求 |
| 模块职责与详细需求大段重复 | 总需求写一句职责，详细需求写定位和细节 |
| 把没想清楚的事写进“明确不做” | 移到待确认，并说明影响 |
| 功能没有编号 | 每个功能必须有 `Mx-Fyy`，否则无法建索引 |
| 全文出现第二套术语 | 统一用业务方原话，首次出现处解释 |
