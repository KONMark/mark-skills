# 需求转开发文档（req-to-spec）

## 这个 Skill 做什么

把用户手里的需求材料，整理成两份职责分明、可直接用于开发与验收的文档：

| 文档 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 总需求文档 | 做什么、为什么做、做到什么程度 | 背景、范围、核心流程、模块职责、主体、状态、功能清单、项目要求 |
| 详细需求文档 | 每个功能具体怎么用、系统怎么校验 | 字段表、操作步骤、规则、示例、不做清单、待确认清单 |

**核心原则：只整理，不发明。** 没有来源的内容，要么问用户，要么标“待确认”，不允许写成确定事实。

## 开始前

1. 读完用户提供的全部材料，不要只读开头。
2. 如果材料是文件路径，逐个打开；Excel、图片等无法直接读取的，记下文件名和用途，并请用户粘贴关键列名或内容。
3. 如果用户提供的是已有文档并说“重写 / 升级 / 按新结构整理”，把原文档当作素材：已确认的结论保留，不重复追问。
4. 确认输出位置。默认规则：
   - 当前项目已有 `开发文档/v*/需求/` 结构时，沿用 `开发文档/v<版本>/需求/`。
   - 否则使用当前目录下的 `需求文档/`。
   - 用户指定了位置就按用户指定。
5. 输出文件固定为：`总需求文档.md`、`详细需求文档.md`，以及工作文件 `需求事实清单.md`。
6. 目标文件已存在时，先询问是覆盖、另存版本还是只生成差异，不要直接覆盖。

## 工作流程

必须按顺序执行。每一阶段的产出都是下一阶段的输入，不要跳阶段直接写文档。

### 阶段 0：读材料 + 信息体检

按 `references/gap-checklist.md` 的维度逐项盘点输入：

| 维度 | 状态 | 已知内容 | 缺口 |
| --- | --- | --- | --- |
| 背景与目标 | 已知 / 部分 / 缺失 | … | … |
| 使用角色与权限 | … | … | … |
| 本期范围 | … | … | … |
| 核心流程 | … | … | … |
| 模块与功能 | … | … | … |
| 关键主体与字段 | … | … | … |
| 状态与规则 | … | … | … |
| 数量、金额、精度、编号 | … | … | … |
| 异常与边界 | … | … | … |
| 历史数据与迁移 | … | … | … |
| 非功能要求 | … | … | … |

然后：

- 只对**关键缺口**提问（清单中标记为“必须”的维度），最多两轮，每轮 3～5 个问题。
- 每个问题给出你建议的默认答案，用户可以直接说“按默认”，降低回答成本。
- 非关键缺口不要追问，直接记入“待确认”，继续往下做。
- 发现材料内部矛盾时，单独列出并请用户裁决；不允许自己挑一个。
- 用户明确说“你决定”的内容，写进文档时用“暂按……处理（待确认）”，不能写成已确认。

阶段 0 结束的标志：关键缺口已问过一轮，用户给出回答或授权按默认处理。

### 阶段 1：建立事实清单

在输出目录创建 `需求事实清单.md`，这是内部工作文件，不作为交付物展示。

| 编号 | 事实 | 类别 | 来源 | 状态 |
| --- | --- | --- | --- | --- |
| F001 | 客户下单后提供大部分材料 | 流程 | 需求文档 §1 | 已确认 |
| F002 | 送货数量不得超过欠货量 | 规则 | 用户 2026-11-19 确认 | 已确认 |
| F003 | 是否需要库存预警 | 功能 | 未提及 | 待确认 |

要求：

- `类别` 使用：背景、范围、角色、流程、模块、实体、字段、状态、规则、精度、非功能。
- `来源` 必须具体到文件名 + 章节，或“用户 YYYY-MM-DD 确认”。
- `状态` 只有两种：`已确认`、`待确认`。推断出来的内容不能标为已确认。
- 至少覆盖：每个模块、每个主体、每个状态、每条关键规则、每项范围边界。

后续两份文档中的所有字段、规则、状态都应能在这张表里找到出处。

### 阶段 2：生成总需求文档

先出**骨架**，不要一次性写全文：

1. 产品一句话与定位。
2. 本期范围 / 明确不做。
3. 主流程步骤。
4. 模块总表（模块、职责、使用角色、流程位置、详细需求章节）。
5. 每个模块的功能清单（带编号 `M1-F01`）。

把骨架给用户确认。用户确认模块划分、范围边界和功能清单后，再补齐背景、流程说明、主体、状态、规则、项目要求。

格式必须遵循 `references/total-spec-template.md`，特别是：

- 顶部四行元信息表。
- 一级标题写 `# 1.`、`# 2.`……，二级写 `## 1.1`。
- 段落先结论后细节，粗体引导词加列表。
- 待确认内容写在括号里「（……待确认。）」，不集中另开一节。
- **不写字段表，不写操作步骤**；这些属于详细需求。

### 阶段 3：生成详细需求文档

顺序：

1. 先写第 1 节文档说明和第 2 节系统总览，包括：
   - 模块总览表（含“总需求章节”列）。
   - 角色与可见范围表。
   - 功能总索引表（模块、功能、编号、总需求条目、本文章节）。
2. 再按“前置流程 → 主流程 → 系统管理”的模块顺序逐个写。
3. 每写完一个模块，回填功能总索引和该模块的规则汇总。
4. 最后写通用规则、本期不做、需要确认的事项、文档使用说明。

每个模块固定四段：

- 这个模块解决什么问题（3～5 行，附“对应总需求 §4.x”）。
- 系统保存哪些资料（每张表一张字段表：字段 / 填写方式 / 说明）。
- 功能清单（每个功能：用途 / 操作 / 规则）。
- 本模块必须记住的规则。

硬性要求：

- 功能块与总需求的功能编号一一对应，**不增不减**。需要新增功能时，先回写总需求并让用户确认。
- 「操作」按员工实际点击顺序写，用“点击、选择、填写、核对、确认”等动作词。
- 「规则」写成可判定对错的完整句子，避免“尽量”“适当”“合理”这类词。
- 关键计算给出一个具体算例。
- 待确认事项集中到最后一节，正文用括号指过去；不要在每个功能里重复列。
- 只写业务与使用，不写表名、接口、SQL、框架等技术实现。

文件较长时，先写带标题的骨架，再逐模块用编辑方式填充；不要把整篇一次性生成后丢内容。

格式遵循 `references/detailed-spec-template.md`。

### 阶段 4：自检与交付

按 `references/self-check.md` 逐项检查，不通过就修。重点：

- 总需求每个 `Mx-Fyy` 在详细需求都有对应功能块。
- 每个主体有字段表，每个状态有进入/离开条件。
- 精度、编号、权限等全局规则只定义一次，其他章节引用而不复述。
- 两份文档的范围、模块、功能清单完全一致。
- 没有无来源的字段、规则、模块。
- “本期不做”只包含用户明确确认不做的事；只是没想清楚的，写“待确认”。

最后向用户报告：模块数、功能数、待确认事项数、生成的文件路径，以及自检中仍未通过或需要用户裁决的点。

## 输出格式约定

- 语言跟随输入材料；输入为中文时输出中文。
- 日期使用 `YYYY-MM-DD`，数字使用千分位（如 1,000 件），金额和单价的小数位按项目约定，未约定时在“通用规则”中明确一次。
- 文档中的模块编号、功能编号一旦生成，后续修改只增不改号。
- `需求事实清单.md` 默认保留在输出目录，方便下一轮修改；用户要求时再删除。

## 绝对不要

- 不要编造模块、字段、状态、规则、编号或业务背景。
- 不要把“没想清楚”写成“本期不做”。
- 不要在总需求里写字段表和逐步操作。
- 不要在详细需求里新增总需求没有的功能。
- 不要静默处理材料中的矛盾，也不要替用户做业务取舍。
- 不要用未解释的 ERP 术语；面向工厂人员的文档要能直接读懂。
- 不要覆盖已有文档而不询问。
- 不要在自检未通过时宣称已完成；如实说明剩余问题。
