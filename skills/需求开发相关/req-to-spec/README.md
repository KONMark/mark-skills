# req-to-spec

把原始需求材料整理成类 SDD 文档：先厘清「做什么、做到什么程度」，再拆到「每个功能怎么用、怎么校验」，输出可直接用于开发与验收的《总需求文档》和《详细需求文档》。

**核心原则：只整理，不发明。** 没有来源的内容，要么问用户，要么标「待确认」。

## 核心流程

```
读材料 → 信息体检（补关键缺口）
       → 建事实清单（可溯源）
       → 总需求骨架确认 → 补齐总需求
       → 按模块写详细需求（功能编号一一对应）
       → 自检交付
```

1. **信息体检**：按缺口清单盘点背景、范围、流程、模块等，只追问关键缺失项。
2. **事实清单**：把已确认与待确认事实落表，保证后续文档可溯源。
3. **总需求**：先出模块 / 功能骨架给用户确认，再补背景、流程、主体与状态。
4. **详细需求**：按功能编号展开字段、操作步骤与规则，不增不减。
5. **自检**：核对两份文档范围、模块、功能是否一致后交付。

## 输入 / 输出

### 输入

任意形式的需求材料，例如：

- 口头描述、聊天摘录、访谈记录
- 已有需求 / PRD / 旧系统说明
- Excel、图片等线索（需用户补充关键列名或内容）

### 输出

默认写到 `开发文档/v*/需求/`（若项目已有该结构），否则写到当前目录下的 `需求文档/`：

| 文件 | 用途 |
| --- | --- |
| `总需求文档.md` | 背景、范围、核心流程、模块职责、功能清单 |
| `详细需求文档.md` | 字段表、操作步骤、规则、示例、待确认清单 |
| `需求事实清单.md` | 内部工作文件，记录事实来源与确认状态 |

两份正式文档通过功能编号（如 `M1-F01`）双向索引，保证模块与功能拆分一致。

## 目录结构

```
req-to-spec/
├── SKILL.md                          # Skill 主说明与工作流
├── README.md                         # 本文件
└── references/
    ├── gap-checklist.md              # 信息体检维度与提问指引
    ├── total-spec-template.md        # 《总需求文档》模板
    ├── detailed-spec-template.md     # 《详细需求文档》模板
    ├── style-guide.md                # 语言、术语、编号约定
    └── self-check.md                 # 交付前自检清单
```
