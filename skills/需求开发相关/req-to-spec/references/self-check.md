# 交付前自检清单

阶段 4 使用。逐项检查，全部通过才能宣称完成。不通过的项要修，或在交付说明中如实列出。

## 1. 覆盖检查

- [ ] 总需求第 2 节的每个模块，在第 4 节都有对应的模块明细。
- [ ] 第 4 节模块总表的每个模块，在详细需求都有独立章节。
- [ ] 总需求每个功能编号 `Mx-Fyy`，在详细需求都有同名功能块。
- [ ] 详细需求没有出现总需求未定义的功能编号。
- [ ] 每个核心主体在详细需求都有字段表。
- [ ] 每个有状态的资料表，都写了状态名、含义、进入条件和离开条件。
- [ ] 主流程的每一步都能在某个模块的功能里找到落点。
- [ ] 用户明确提出的每条规则，都在文档中有对应位置。

## 2. 证据检查

- [ ] 抽查 10 条字段和规则，都能在事实清单中找到来源。
- [ ] 没有任何“凭空出现”的模块、字段、状态、角色。
- [ ] 所有推断内容都写成“暂按……处理，待确认”，没有写成确定事实。
- [ ] 事实清单中标记“待确认”的项，在详细需求最后一节都有对应条目。
- [ ] 没有把用户没说过的事写进“本期不做”。

## 3. 一致性检查

- [ ] 两份文档的模块名称完全一致。
- [ ] 两份文档的功能清单和编号完全一致。
- [ ] 范围表述一致：总需求“本期要做”覆盖详细需求的所有模块，没有遗漏或超出。
- [ ] 同一数字、精度、编号规则只在通用规则定义一次，其他位置引用而不复述。
- [ ] 同一个概念全文只有一个叫法。
- [ ] 日期、数量、金额格式统一。
- [ ] 跨模块的计算口径一致，例如累计数量、欠量、金额的算法在两处描述相同。

## 4. 结构检查

- [ ] 总需求有顶部元信息表，四行齐全。
- [ ] 总需求没有字段表、操作步骤和技术实现。
- [ ] 详细需求每个模块都按“问题 → 资料 → 功能 → 规则”组织。
- [ ] 每个功能块都有用途、操作、规则；确实没有操作的，已说明原因。
- [ ] 字段表三列齐全，填写方式只使用规定词。
- [ ] 待确认事项集中在最后一节，正文没有散落的完整待确认列表。
- [ ] “本期不做”集中成节，正文没有反复声明。

## 5. 语言检查

- [ ] 没有未解释的 ERP 术语或缩写。
- [ ] 没有“尽量”“适当”“合理”“相关”等不可判定的词。
- [ ] 规则能构造出通过和不通过的例子。
- [ ] 关键计算有具体算例。
- [ ] 操作步骤按员工实际点击顺序书写。
- [ ] 面向工厂人员能直接读懂，不需要开发在旁边解释。

## 6. 交付检查

- [ ] 文件写入用户确认的目录，文件名正确。
- [ ] 顶部日期为生成当天。
- [ ] 没有覆盖用户未同意覆盖的文件。
- [ ] 事实清单保留在输出目录。
- [ ] 交付说明中写明：模块数、功能数、待确认数、文件路径、仍未通过或需用户裁决的点。

## 不通过时的处理

- 覆盖或一致性问题：回到对应阶段补写，不靠文末补一句掩盖。
- 证据问题：删除无来源内容，或改为待确认。
- 语言问题：按 `style-guide.md` 重写相关段落。
- 用户未确认的业务取舍：不要自行决定，列成问题交还用户。
